# Task: Netty 迷你 RPC 项目（项目驱动主线）

> 这是 Phase 4 的核心任务，也是整个路线的**跳槽节点**。
> 做法：**项目驱动** —— 不再先学完理论再做项目，而是定一个必须用上基础技术的项目，边做边学。
> 铁律：**核心代码自己写，AI 只讲不写。**

## 项目目标

做一个能跑通的「迷你 RPC 框架」：

- 服务端：Netty 服务器，管理多个客户端连接
- 客户端：通过接口调用，像调用本地方法一样调用远端方法
- 中途必须用上：集合、并发、网络、IO、Netty、反射

最终交付：

1. 一个能跑起来的 Maven 工程（服务端 + 客户端）
2. 能演示：客户端调接口 → 服务端执行 → 返回结果
3. 一份项目文档（架构图、协议设计、遇到的问题）
4. 能 10 分钟讲清楚整个项目

## 为什么选这个项目

因为它**逼着**你用上这条路线上的基础技术，不用就做不下去：

| 项目环节 | 逼你用到的技术 | 对应基础知识 |
|---|---|---|
| 管理在线连接 | ConcurrentHashMap / ChannelGroup | 集合、equals/hashCode |
| 协议消息定义与判等 | equals / hashCode | 集合基础 |
| 自定义编解码 | ByteBuf、字节操作 | IO、网络基础 |
| 粘包拆包 | 长度字段协议 | TCP、IO 模型 |
| 多个客户端并发 | 线程池、EventLoop | 并发、JVM |
| 请求-响应配对 | requestId + Future/等待唤醒 | 并发、集合 |
| 像本地一样调用 | 动态代理、反射 | Java 基础 |
| 服务注册与路由 | Map 存服务实例 | 集合 |

**关键点**：这些都是「不学就卡住」的知识点，所以学了立刻用，不容易忘。

## 铁律：AI 使用规则

你现在的短板是「代码基本靠 AI 写」。如果做项目时继续这样，这个项目做完你还是学不会。

**AI 可以做：**

- 解释一段代码是干什么的
- 解释报错信息
- 对你的代码做 review，指出问题
- 出题考你（比如「你的 Decoder 怎么处理半包？」）
- 陪你讨论设计取舍

**AI 不可以做：**

- 直接让 AI 写核心类（编解码器、等待响应逻辑、动态代理）
- 直接让 AI 写「我不知道怎么下手」的那部分
- 复制 AI 代码后不去理解

**每次让 AI 帮忙后，必须能用自己的话复述一遍。复述不出来 = 没学会。**

## 怎么用参考代码和示例

写新东西一定会参考示例（比如官方 Echo 示例）。这不算作弊，但要用对方法：

```
1. 先看示例，理解思路（只看不抄）
2. 关掉示例，凭理解自己写
3. 卡住的地方再看一眼示例，然后继续自己写
4. 写完对照示例，找差异
5. 隔一两天，删掉自己写的，再凭记忆写一遍
```

**关于复制粘贴**：复制官方示例和让 AI 写，过程不同但结果可能一样 —— 如果复制完就结束、不读不改，那和 AI 写没有区别。
区别在于**复制之后你做了什么**：读懂 → 改 → 删掉重写，才叫学会。

## M0 环境搭建 + 最小 Echo

**目标**：让 Netty 服务端起得来、客户端连得上、能收发消息。

**要做什么**

1. 新建 Maven 工程，引入 Netty 依赖
2. 写 `EchoServer`：启动服务、监听端口
3. 写 `EchoClient`：连接服务、发消息、收消息

**自己写什么**

- 服务端 `ServerBootstrap` 启动流程那部分
- 客户端 `Bootstrap` 连接流程那部分

**参考资源**

- Netty 官方用户指南（Echo 示例）：https://netty.io/wiki/user-guide-for-4.x.html
- Netty 官方示例代码：https://github.com/netty/netty/tree/4.1/example
- 怎么用：先看官方 user guide 的 Echo 部分，理解流程后关掉，自己写一遍
- 重点看：`ServerBootstrap` 的启动链路、`ChannelInitializer`、`pipeline`

**用到的基础知识**

- Java 基础、Maven

**验收标准**

- [ ] 服务端能启动并监听端口
- [ ] 客户端能连上并发送消息
- [ ] 服务端能把消息原样返回
- [ ] 控制台能看到收发日志

## M2 自定义协议 + 编解码 + 粘包拆包

**目标**：不再用 String 直传，定义自己的消息格式，解决粘包拆包。

**要做什么**

1. 定义消息格式：

```text
+--------+--------+--------+--------+----------+
| 魔数   | 版本   | 类型   | 长度   |   body   |
| 4 字节 | 1 字节 | 1 字节 | 4 字节 |   N 字节 |
+--------+--------+--------+--------+----------+
```

2. 写编码器 `MessageEncoder`
3. 写解码器 `MessageDecoder`（继承 `ByteToMessageDecoder`），处理半包和粘包
4. 用 `LengthFieldBasedFrameDecoder` 或自己写拆包逻辑

**自己写什么**

- 消息类 `Message`（字段 + equals/hashCode）
- **解码器的拆包逻辑（重点，这里最容易卡住）**

**用到的基础知识**

- 字节与位运算、ByteBuf
- TCP 为什么会有粘包拆包
- equals / hashCode（消息对象）

**怎么验证**

- 一次性连发 3 条消息，服务端能正确拆成 3 条
- 分两次发包（模拟半包），服务端能正确拼成 1 条

**验收标准**

- [ ] 自定义协议能用
- [ ] 粘包场景处理正确
- [ ] 半包场景处理正确
- [ ] 能解释「为什么需要长度字段」

## M3 连接管理（集合实战）

**目标**：服务端能管理多个客户端连接。

**要做什么**

1. 用 `ConcurrentHashMap<String, Channel>` 或 `ChannelGroup` 保存连接
2. 客户端上线时注册，下线时移除
3. 实现：按 userId 找连接、广播消息

**自己写什么**

- 连接注册 / 移除逻辑
- 按 userId 查找
- 广播

**用到的基础知识**

- **HashMap / ConcurrentHashMap（这就是集合的实战）**
- **equals / hashCode（如果用对象做 key）**
- 为什么这里要用 ConcurrentHashMap 而不是 HashMap

**验收标准**

- [ ] A 发消息，B 能收到（广播）
- [ ] 客户端断开后，Map 里的连接被清理
- [ ] 能解释为什么选 ConcurrentHashMap

## M4 心跳与空闲检测

**目标**：服务端能发现「假死」的连接并清理。

**要做什么**

1. 服务端加 `IdleStateHandler`
2. 客户端定时发心跳消息
3. 服务端超时未收到心跳就关闭连接

**自己写什么**

- 心跳 handler
- 超时处理逻辑

**用到的基础知识**

- 定时任务、事件驱动
- 网络：为什么会有死连接

**验收标准**

- [ ] 客户端正常时不会被踢
- [ ] 客户端异常断开后能被检测到并清理
- [ ] 能解释心跳的作用

## M5 请求-响应模型（RPC 地基）

**目标**：客户端发请求能拿到**对应的**响应，而不是靠广播碰运气。

**要做什么**

1. 消息加 `requestId`
2. 客户端发送前把 `requestId` 和一个「等待中的结果」存进 Map
3. 收到响应后按 `requestId` 唤醒等待方
4. 支持超时

**自己写什么**

- **等待 / 唤醒逻辑（重点，这里会用到并发）**
- requestId 的生成与映射

**用到的基础知识**

- 并发：`CompletableFuture` 或 `wait/notify`
- 集合：`ConcurrentHashMap<requestId, Future>`
- 超时处理

**验收标准**

- [ ] 客户端能像调用普通方法一样拿到返回值
- [ ] 并发发多个请求，结果不会串
- [ ] 超时能报错，不会一直卡住
- [ ] 能解释「为什么需要 requestId」

## 卡住了怎么办（处理流程）

按顺序试，不要直接跳到最后一步：

1. **自己查**：官方文档、API 文档、源码
2. **问 AI 解释**：只问「这是什么意思」，不要问「帮我写出来」
3. **让 AI 出题**：让 AI 就卡住的知识点考你
4. **缩小问题**：写一个最小 demo 单独验证这一点
5. **最后才看示例**：看完要删掉重写

**卡住是正常的。卡住说明你碰到了真正要学的东西。**
