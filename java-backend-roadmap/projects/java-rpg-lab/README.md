# Java RPG Lab：项目驱动的 Java 后端学习路线

> 当前目标：从已有的 Spring Boot + MyBatis/MyBatis-Plus CRUD 能力出发，通过开发一个可玩的 Java 控制台 RPG，逐步建立独立设计、编码、调试和测试能力；后续再探索数据库、网络通信、Netty 与游戏服务器开发。
>
> 本文是新的候选主线。原有 Java 集合学习记录和 Netty mini RPC 计划保留作为历史积累/后续选项，不要求现在继续推进旧任务。

## 1. 为什么选择控制台 RPG

学习者已经能够完成简单的 Spring Boot + 数据库 CRUD，例如从学生表查询数据、通过 Controller 提供 API。当前难点更可能出现在需求拆解、模块设计、业务逻辑、调试和边界情况上，而不是基础 CRUD 本身。

控制台 RPG 提供一个有趣且可以逐步扩展的载体：

- 从战斗和角色状态开始，练习面向对象设计与业务规则。
- 加入物品、装备、背包和存档，练习集合、数据建模和持久化。
- 加入地图、任务和副本，练习模块协作、状态管理和测试。
- 后续将游戏逻辑与存储、API 分离，再逐步探索多人交互、TCP、协议、并发和 Netty。

控制台 RPG 是能力训练项目，不等同于商业游戏或完整游戏服务器。项目应优先保持可运行、可理解、可持续迭代，不追求一次实现大型游戏。

## 2. 学习原则

1. **项目优先，知识按需补充。** 不要求先学完某个知识章节才开始写功能。
2. **先做最小版本。** 每个阶段只加入少量新概念，保证每次学习都能看到运行结果。
3. **核心逻辑由自己负责。** AI 可以解释、给提示、Review 和帮助设计测试，但避免直接生成整个功能后只复制运行。
4. **以能力验收，不以代码量验收。** 能解释设计、修改需求、处理错误并验证行为，才算掌握。
5. **接受不稳定的学习时间。** 精力差时完成 15–20 分钟的小任务也可以；正常时学习 30–60 分钟；周末按精力安排较长开发时段。
6. **每周复盘并调整。** 如果任务太难，缩小范围；如果已经掌握，不必为了完成清单而重复学习。
7. **求职导向但不急于堆技术。** 每个阶段记录它锻炼的工程能力，并结合目标岗位要求调整后续路线。

## 3. 长期演进路线

| 阶段 | 项目成果 | 主要训练能力 | 暂定技术 |
|---|---|---|---|
| 1. 最小可玩 RPG | 角色与怪物回合制战斗 | 类与对象、职责划分、业务规则、控制台交互 | Java |
| 2. 角色成长与物品 | 经验升级、背包、装备、商店 | 集合、数据建模、规则校验 | Java |
| 3. 地图与任务 | 地图探索、任务、掉落、副本 | 模块设计、状态管理、测试 | Java、JUnit |
| 4. 存档与持久化 | 角色进度可保存和恢复 | 文件读写、持久化边界、数据模型演进 | Java；后续可选 H2/MySQL |
| 5. 后端 API | 服务端提供角色/背包等 API | 分层设计、HTTP、事务、数据库访问 | Spring Boot、MyBatis/MyBatis-Plus、MySQL |
| 6. 多人交互原型 | 两个客户端通过服务端交互 | 会话、消息协议、共享状态、错误处理 | TCP；需要时引入 Netty |
| 7. 服务器进阶 | 房间/副本、消息广播、压测与部署 | 并发、线程安全、性能、可观测性 | 按需求选择 Netty 等技术 |

阶段不必严格线性执行。例如，如果前期游戏玩法范围已经足够，可以较早引入数据库；多人网络部分应在单机游戏逻辑相对清晰后开始。是否继续深入 Netty，依据实际兴趣、项目进度和招聘要求决定。

## 4. 阶段 1：最小可玩 RPG

### 4.1 范围控制

第一个版本只做一个简单的回合制战斗，不做地图、背包、装备、数据库、网络通信或复杂战斗公式。

最低功能：

- 创建一个玩家角色。
- 创建一种怪物。
- 显示玩家和怪物的当前状态。
- 玩家选择攻击或查看状态。
- 玩家与怪物轮流行动。
- 生命值降至 0 时结束战斗。
- 胜利或失败后显示结果。
- 对无效输入进行处理，避免程序意外崩溃。

建议先用固定数值或简单公式计算伤害，之后再考虑随机伤害、暴击等机制。

### 4.2 建议的初始对象

这只是设计起点，允许在实现前调整，不要求机械照搬。

- `Player`：玩家的名称、生命值、攻击力和经验值。
- `Monster`：怪物的名称、生命值和攻击力。
- `BattleService` 或 `Battle`：组织战斗流程、判断战斗结束。
- `Game`：处理主菜单与控制台输入。

不要一开始创建过多类。只有当某段逻辑有清晰职责、确实需要独立管理时，再考虑拆分。

### 4.3 建议的开发顺序

- [ ] T1：写下最小玩法规则，用几句话说明玩家和怪物如何战斗。
- [ ] T2：设计玩家和怪物需要保存哪些状态。
- [ ] T3：创建对象并能显示初始状态。
- [ ] T4：实现一次攻击与生命值变化。
- [ ] T5：实现玩家与怪物轮流行动。
- [ ] T6：实现胜负判断与战斗结束。
- [ ] T7：增加控制台菜单与无效输入处理。
- [ ] T8：手动测试关键情况，并写下复盘。

每项可以拆成更小的任务。如果卡住，不必一次解决整个阶段。

### 4.4 阶段 1 验收标准

- 能从程序入口开始讲解一次战斗的完整流程。
- 能说明每个核心类的职责，以及为什么这样划分。
- 能自己增加一种怪物或修改攻击规则。
- 能处理生命值为 0、错误菜单输入等边界情况。
- 能写出至少几条测试场景，后续可逐步引入 JUnit。
- 能在不让 AI 重写整个项目的情况下修复一个 bug。

## 5. 后续阶段的功能候选

### 阶段 2：角色成长与物品

建议依次添加：

- 经验值与升级规则。
- 物品模型与背包。
- 药水使用与数量扣减。
- 装备属性与属性计算。
- 金币与商店购买。

重点问题：物品数量为 0 时怎么办？金币不足时是否允许购买？装备更换后属性如何更新？这些规则应由代码和测试共同保证。

### 阶段 3：地图与任务

候选功能：

- 多个地点和移动规则。
- 怪物遭遇与战斗触发。
- 任务状态与任务奖励。
- 战利品掉落。
- 副本进入与完成条件。

重点练习模块之间如何协作，以及如何避免任务、战斗和奖励逻辑相互耦合。

### 阶段 4：存档与持久化

可以先选择最简单的文件存档，明确需要保存哪些状态；之后再考虑数据库。

进入 Spring Boot 与 MyBatis/MyBatis-Plus 阶段时，再练习：

- 表结构和主键设计。
- 角色、物品、装备等数据的关联关系。
- 事务和异常处理。
- 数据访问层与游戏规则之间的边界。

工作电脑若不方便安装数据库，可以用 H2 快速练习；个人电脑可继续使用已有的 MySQL 环境。H2 不应完全替代 MySQL 的实践。

### 阶段 5：后端 API

将适合服务端管理的数据和游戏逻辑逐步暴露为 HTTP API。不要把所有游戏逻辑塞进 Controller；Controller 负责请求与响应，业务规则由独立的服务层处理，存储细节由 Repository/Mapper 处理。

### 阶段 6：多人交互与服务器

先定义最小目标，例如两个控制台客户端能够连接到同一个服务端并互相发送消息。之后再逐步增加玩家会话、消息类型、心跳、断线处理、房间或多人副本。

只有当项目确实需要网络通信时再引入 Netty；不要为了学习 Netty 而提前把简单的单机逻辑改造成复杂网络架构。

## 6. AI 协作规则

推荐的协作顺序：

1. 自己先写需求和预期行为。
2. 自己画出流程或列出类与方法。
3. 自己尝试实现；卡住时说明已经尝试过什么。
4. 先请求提示、原理解释或局部 Review，而不是直接要求完整实现。
5. 实现后让 AI 帮忙检查边界情况并提出测试场景。
6. 最后关闭参考答案，自己解释或修改一个关键行为。

允许使用 AI 的场景：

- 解释编译错误或运行时异常。
- 对已有设计提出改进建议。
- 检查潜在边界情况。
- 帮助编写测试清单。
- 比较两种设计的优缺点。

每完成一个功能，至少做一件验证掌握程度的事：独立解释流程、修改一个需求、修复一个问题或重写关键方法。

## 8. 第一周建议

目标不是完成一个完整 RPG，而是建立最小可运行版本。

- 第一次：确定战斗规则，创建工程与核心对象。
- 第二次：实现攻击与生命值变化。
- 第三次：实现轮流行动与战斗结束。
- 第四次：加入控制台交互和输入校验。
- 第五次：手动测试、修复问题、写复盘。

时间只作参考。每次学习结束时，记录下一步要做的具体动作，让下次打开项目时不需要重新决定从哪里开始。
